# Native addon example

This separate NeoForge mod consumes only the staged `design.inherent:reform` Maven artifact. It does not use the library's source sets, Compat, Skyweave or the modpack. The ordinary example JAR excludes the opt-in native probe.

`FileFormatsExample` uses the shared `ClientFileSettings` lifecycle for explicit properties, existing bare JSON and an independently implemented `TextStore` format. `--files-only` selects its two-client native probe: distinct saved/default values, omitted defaults, comments/CRLFs, actual save/no-op, custom representation, malformed-source Retry and fresh-JVM publication/closure. Registration controls separately refuse owned-file aliases and portable-case collisions before initialization. Definitions validate their declared defaults once; file/runtime initialization is a separate observation. [Client file registration](../../docs/development/client-files.md) owns the API contracts; verification records actual tested artifacts.

`StartupExample` explicitly selects its own bounded bootstrap input before registering saved-choice editors. `--startup-only` changes the saved files after that selection, then exercises known and unavailable active values, malformed saved data, source repair, review/save/restart captions and another JVM's actual new bootstrap. A separate probe-owned value policy holds real worker-side owner construction until native game shutdown; it checks settled closure and absence of a source effect. This adds no production hook and does not claim qualification of a foreign mixin loader or arbitrary feature bootstrap.

`NativeExample` declares a small typed preference record through public record derivation. Its physically client-only `ClientExample` uses the [client JSON factory](../../docs/development/client-files.md), explicit menu registration and the `reformprefs` native client command. The library supplies native setup, bounded workers, owned storage, shared GUI/command operations, the generated form and shutdown. The example supplies no executor, serializer or editing-session infrastructure.

`CreationExample.editor(parent, original)` separately demonstrates the public world-recipe factory for a bounded three-layer flat-world soil-depth setting. It preserves unedited dimensions through the native replacement API and registers no replacement editor for vanilla presets. The native form runner executes it in a real creation screen, without creating a playable world.

`ServerPolicyExample` binds an explicitly world-rooted JSON policy and a real registered SERVER TOML config through [server settings](../../docs/development/server-settings.md). The library supplies server lifetime, workers, source restrictions and shared editing. Native serializers and callbacks remain native. `native_addon_server_probe.py --policies` selects two isolated dedicated boots with distinct seeded/default values, source/permission refusals, competing drafts, actual file/native saves, malformed retention, editor cleanup, deliberate scope replacement and native-stop closure.

The example registers `/reformpolicy file` and `/reformpolicy toml` through the shared native server command factory. The dedicated probe observes real console feedback and compares it with the saved file and runtime handle. The integrated probe issues actual player commands through the native play connection. It observes an independent command draft, performs a native respawn and verifies stale operation refusal followed by a fresh saved baseline.

`ClientExample.worldPolicy` opens those same sources through `IntegratedSettings.screen`. `native_form_probe.py --integrated-only` uses a disposable playable flat world to check host permission, stale client permission, abandoned admission, real JSON and TOML saves, FML callback thread, disconnect and fresh-JVM reopen. The default native form suite includes these two boots.

`RegisteredExample` binds actual CLIENT and COMMON registrations through the [native client factory](../../docs/development/native-settings.md#physical-client-registration), retaining a legacy native filename with spaces. `--registered-only` selects native review/submission, real setters and owner-thread callbacks, warmed restart-cache observations, client Brigadier, compact COMMON-default editing, explicit FML unload/load and Retry, fresh-JVM data and game-shutdown controls. A bounded event trace distinguishes startup/file-watcher wrapper replacement from owner-thread Save. Native loaded values and generic application declarations do not stand in for domain-effective observations.

`WorkflowExample` composes JSON, Controls and both native registrations through [retained client workflows](../../docs/development/client-workflows.md). `--workflow-only` checks invalid drafts/history across navigation, real key capture, independent persistence/receipts, pending-save exit refusal, competing-owner revision guards, explicit editor replacement, unexpected-navigation cleanup, native compact reflow and another JVM's saved values. Its UI draft lifetime is distinct from each borrowed document runtime. Game shutdown must also close an opened workflow that was never displayed.

`--batch-only` selects complete-vector preflight over those four ordinary owners, typed cross-document validation, exact captured field inspection, stale-review refusal, measured combined review, ordered native saves, separate staged receipts and actual fresh-JVM values. Clean Controls participate as a read-only check without writing Options. The optional `DocumentBatch.Validator` belongs to the consumer and runs on a worker over complete immutable candidates; it does not query a native registry or replace any owner.

`WorldDefaultsExample` supplies a new owned JSON defaults file and an optional existing-format source with deferred creation through the shared file factory. `--defaults-only` exercises three disposable clients: actual unsaved-default editing and source saving without changing an open native creation context; registered-source Preview/Stage/Undo/Redo followed by separate native Apply; saved reopening in another JVM; and malformed-source retention plus explicit repair/Retry. The flat-world example remains the domain owner. Its dimensions, compilation and original-context rules are not implemented in the library or the defaults source.

Run `./gradlew --no-daemon check build` from the repository root to compile this example and its probe against the exact candidate artifact. This compiles native APIs without launching a game. It also runs the independent headless consumer and core/tooling checks.

For a disposable client check, first build/stage the library, obtain sustained desktop focus, then run from the repository root:

```sh
python3 tools/native_form_probe.py --java-home /path/to/jdk21
```

The runner refuses an existing `examples/native/runs/client`, creates its own marked fixture and runs bounded 2 GiB Minecraft clients sequentially. The probe exercises registration refusals, actual menu entry, native fields/invalid drafts/save/reflow/close/reopen, persisted preferences in a second JVM, malformed-file retention/recovery, a pending retry started by an initialization observer and settled at native shutdown, recursive/reference/numeric/dependency controls, collection selection, admitted import and manual conflict review. Each persisted workflow also reopens in a second JVM. `--lifecycle-only` selects the shutdown control; `--recipe-only` selects native original-context recipe controls; `--structured-only`, `--references-only`, `--numeric-only`, `--dependencies-only`, `--collections-only`, `--imports-only` and `--conflicts-only` select their respective controls/reopen. Registered command suites have separate options described below. The first client also posts the actual client command-registration event and runs native Brigadier operations on the same GUI-saved document, covering invalid input, staged edits, validation, comparison, export/copy components, actual save/publication and retained status/cancel. Its feedback sink is captured at the main menu; this does not qualify a player chat packet or physical clipboard. Reports/screenshots go to ignored `build/reports/native-form/`. Only the matching task-owned fixture and logs are removed. Personal instances, servers and worlds are not used.

`StructuredExample` is an independently registered client JSON profile for those recursive controls. The probe edits actual native inputs/buttons, follows row identity across copy/move, repairs duplicates, restores invalid inactive values and confirms obsolete widget callbacks cannot target restored branches. It preserves unchanged disk until explicit Save and checks the resulting runtime value and fresh-JVM reopen. This is an inline generated form, separate from the reference-picker and catalog suites.

`CatalogExample` opts the same ordinary client factory into public `FormCatalog` metadata: named profile list members, role maps, a related min/max pair and an absent optional section. `--catalog-only` selects its separate native navigation/save/reopen probe. It checks the existing editor across filtering, page switching, row moves/Undo, hidden invalid input, display-unit preferences, auxiliary return and compact/wide reflow. Actual resource reload selects the example's longer German labels and Unicode font option, then restores both without saving the draft. A deliberately exhausted complete catalog explicitly falls back to the same saved profile. All source effects still use the same owner-backed Save; catalog labels and row UUIDs are not stored. Native qualification and its limits are recorded in [verification](../../docs/development/verification.md), separately from ordinary compilation.

`ReferenceExample` supplies explicit block/tag and client language-resource snapshots through the ready owner, plus a deliberately absent optional donor and an unbound source. It prepares/replaces sources explicitly; ordinary rendering and typing do not enumerate resources. The picker fixture uses native text/pointer events to search/page/inspect, reject malformed/unknown/unavailable choices, refresh a same-label source replacement, retain an over-limit authored ID with diagnostics and repair it. Choosing changes the draft; the fixture separately saves/reopens and checks auxiliary-screen teardown. This example does not replace actual world-specific registry or resource reload policy.

`--review-only` selects the catalog addon's source/value inspection and fresh-JVM reopen controls. It retains invalid input and profile copies, distinguishes baseline/draft/effective values, follows a related diagnostic back to its actual field, filters and expands captured data, checks narrow reflow and exercises native Brigadier `review`. The fixture discards its changes, requires completed-frame diagnostic/narrow captures and verifies editor/factory closure. This runner describes the selected checks; [verification](../../docs/development/verification.md) identifies which artifact has actually passed them. The normal client suite includes this pair.

`--catalog-review-only` runs catalog save/reopen followed by inspection/reopen in one owned fixture. Inspection retains the actual source as a test witness across JVMs, allowing it to verify discarded edits after a prior authored profile change. The aggregate requires both families' entry and completed-frame captures. Long native text input yields between small batches instead of exhausting the bounded operation queue in one tick.

`--close-only` selects ordinary form save/reopen/malformed handling, the file-close pair and original native creation-context controls. `NativeCloseControls` uses public owner/types/operations with real files; test-only worker comparison barriers hold publication or revoke WRITE after persistence. It checks that saved-but-unapplied results and later edits keep the form open, and that explicit application-only recovery preserves file bytes, modification time and replacement identity. It also checks disabled invalid Save, Escape/Keep, reflow/focus, retired callbacks, actual Save and close/reopen and context/worker shutdown. Creation checks separately exercise Apply recipe and close and prevent repeating an unknown admission. All sources stay inside the marked disposable client; no playable world is created.

`--submission-only` adds identified review and actual operation feedback over that public file fixture. Invalid and stale captures cannot submit. A refreshed capture follows shared editor changes; its explicit action passes the exact revision through the existing owner. Actual saved-but-refused publication is recovered through the native application-only button without source replacement. READ revocation clears feedback, Back retains the operation, and cancellation after source replacement drains to its actual receipt while later native input survives. The sequence includes fresh-JVM reopen, read-only inspection, unknown creation-context outcomes and draft-close regressions. Required entry and completed-frame captures cover submission plus wide/compact results. Full native event-method qualification remains distinct from physical-input, full-pack and cost checks.

`NumericExample` declares duration, distance, probability, already stored percent, explicit sliders and an owner-validated min/max pair through the same client factory. Its native fixture distinguishes display-only switches from staged input, checks exact integer refusal and canonical steps, retains a conversion failure whose text otherwise parses as a stored number, and verifies save spelling/caret/selection, narrow reflow, retired callbacks and second-JVM canonical file/runtime values. It starts with a deliberately malformed owned file, repairs it through initialization retry and checks that the successor retains its authored presentation. Actual pointer drags exercise latest-value coalescing. Range repair preserves both endpoints and the owner's diagnostics without clamping the other field. Custom finite-decimal failure controls exercise explicit refusal without rounding exact text.

`DependencyExample` adds local boolean/choice/optional-input gates through the same generated form. Its fixture checks distinct known-false/unknown states, retained invalid values, complete owner validation while inactive, numeric and collection action gating, keyboard explanations and canonical save/reopen. The metadata has no file or authorization authority.

The headless `python3 tools/native_addon_server_probe.py --java-home /path/to/jdk21` separately checks dedicated-side loading and the common derived record codec, with no client document initialized. Its marked loopback-only server uses an ephemeral port, flat seed 42 and a bounded 2 GiB JVM; it stops itself after the controls and removes the fixture/log.

Add `--registered` to the server runner for the separate two-boot [registered native owner](../../docs/development/native-settings.md) controls. This opt-in probe registers its own COMMON spec and exercises the public native owner through the shared editor. It preserves the real native TOML serializer and reload listeners, tests failure/readback/restart behavior and reopens saved state in another JVM. Ordinary example launches do not register that fixture spec.

Both registered boots also exercise the public [reference-source APIs](../../docs/development/references.md): actual block/tag capture and worker index compilation, identifier syntax/default namespace, unknown-versus-default-air behavior, an actual isolated registry's empty tag, whole-producer exhaustion, missing optional supplier and explicitly admitted server resource names. These are common-side lookup controls, without a native picker GUI or full-pack admission claim.

The same boots separately exercise typed structural services against the registered COMMON owner: dynamic list rows, copying/moving/removal, an atomic scalar-membership batch and its one-step undo, stale-target field diagnostics, incomplete scalar input and undo, real native preparation and refusal to Save with read-only access. The fixture retains an unsaved draft and verifies unchanged native TOML bytes; this is not recursive-widget or multi-selection-widget qualification. The native collection controller additionally accepts the actual issued membership edit before its batch/undo checks.

The launches use ModDev source containers for this ordinary example and its separate probe. The library itself loads from the exact packaged Maven JAR, checked both before launch and inside the game. This is not full Phase 1, integrated/remote-server or pack qualification, or a release.

Screenshot requests match the actual rendered screen and read back at the native completed-frame event. Each retains an `-entry.png` plus the fourth matching frame, so viewport-transition pixels are distinguishable from the settled layout. Screenshot capture is test-only and supplies no production rendering adaptation.

`ImportExample` uses the same ordinary client factory and generated **Import…** entry. Its native fixture explicitly drops a local source through the public screen callback, selects value/envelope formats through native input, reviews before/after values, stages/undoes/redoes without saving, refuses malformed/wrong-version input, repairs an invalid imported field and explicitly saves/reopens. A held source proves native capture plus worker reading and cancellation responsiveness. It does not exercise a physical file drop or the operating-system chooser. Failed client runs retain bounded non-symlink crash reports before owned cleanup, keeping root exceptions distinct from ordinary probe assertions.

The same example explicitly registers `reformimports` with a bounded in-memory sample profile. `import list` and the other [registered import commands](../../docs/development/imports.md#registered-native-commands) never accept a path or URL. `--command-imports-only` selects actual native resource-ID/UUID parsing, metadata suggestions, preview/review/stage/Undo/Redo/Save, stale source/catalog/permission controls, held read cancellation and a second-JVM saved reopen. The fixture's separate explicit file registry is disposable and is not installed by ordinary example launches.

`ConflictExample` adds an ordinary min/max/roles definition with complete cross-field validation. `--conflicts-only` exercises the public [manual review screen](../../docs/development/conflicts.md): explicit scalar/whole-collection choices, partial-choice navigation, narrow reflow, failed-read repair, a concurrent writer, invalid resolved input and separate Save/reopen. `--command-conflicts-only` selects native Brigadier review/row choices, actual authority and scope checks, invalid-result feedback and saved reopen. Its coordinator waits on a borrowed fixture worker; command dispatch, permission callbacks and replies remain on Minecraft's native executor. The production service introduces no blocking coordinator.

`KeyExample` independently registers two native Controls mappings, with the primary retaining the same ordinary G/no-modifier baseline shape used by the current Wayfinder registration. It then calls the public [native key factory](../../docs/development/native-keys.md#ordinary-registration-and-entry) with those actual references and registers `reformkeys`. Ordinary use supplies no executor, codec, serializer or editing session. `screen(parent)` permits composition without replacing the addon's existing JSON menu entry.

`--keys-factory-only` selects one-shot native registration timing, an invalid provider without source writes, measured error entry, seventy refused native views and seventy refused JSON views without lifetime exhaustion, GUI draft/Save, native command draft/Save and fresh-JVM reopen. It requires both ready and unavailable registrations to close at actual game shutdown. `--keys-owner-only` separately selects the explicit native Options owner and saved reopen checks. Its fixture coordinator uses a borrowed worker, while actual native setters, permissions and input lookup run on the client executor. An optional setter hook tests reentrant closure; ordinary launches leave it unset.

`--keys-controls-only` selects the same example's explicit generated-form composition with native capture/reset/unbind, key/modifier history, complete draft conflict review, raw repair, stale callbacks, narrow reflow and actual native Controls/save/reopen. Capture and Apply draft leave native mappings/file bytes unchanged until the parent's explicit Save. These advanced controls borrow an admitted actual context; the ordinary factory manages that infrastructure for typical addons. These are native event-method checks, not physical-device or consumer-migration qualification.

On macOS, explicitly run `python3 tools/native_form_probe.py --java-home /path/to/jdk21 --chooser-only --timeout 300` from the library root and `python3 tools/native_chooser_driver.py` in another terminal. These commands require desktop focus and macOS Accessibility access for the invoking host. The opt-in driver targets only AppleScript dialogs descended from the fixture's actual JVM, checks the marked fixture/context and confines the selected path to it. It operates native Cancel and Go to Folder/Choose controls, never the clipboard or an installed client. The fixture requires matched external receipts and actual file preview, then checks abandonment/replacement behavior and unchanged source/draft state. This is not part of the default client suite and does not qualify Windows/Linux dialog automation.

If external automation stops, close its verified task-owned chooser with native Cancel before finishing cleanup. An already entered OS dialog can outlive its Java caller; killing that caller does not prove the dialog closed. Preserve the failed fixture receipt and identify its exact process/window rather than sending global keystrokes or closing unrelated dialogs.
