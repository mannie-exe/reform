# Native platform consumer

This independent native fixture resolves one combined re:form JAR through its staged public Maven module and checks the original artifact hash before compilation and launch. It includes no library source roots. The repository's checked target matrix and catalog supply game, loader, API and Java selections; they remain independent of the selected frozen library version.

Run it from the repository root with the JDK 25 build host:

```sh
python3 tools/native_platform_probe.py --target fabric-1_21_1 --library-version <frozen-version> --java-home /path/to/jdk25
```

Select another explicit matrix target for its native run. `--tested-loader` selects the additional pin only where that target declares one. The helper checks the staged POM and installable product, creates a token-owned loopback-only fixture, performs first delivery and saved reopen in separate JVMs, retains reports and failure causes, then removes its world and runtime files. It refuses an existing fixture directory. No personal client, server or world is used.

Run root verification and native launches sequentially. Root `check` compiles this same independent consumer; rebuilding its classes during a source-container launch can invalidate that running fixture. Distinct target output directories do not isolate two builds of the same target.

Root verification checks compilation against its selected artifact too. Use the matching development handoff for these sources, or a release tag with that release's examples. Native qualification requires a frozen version built with `-Pmod_version=<version>` and selected with `--library-version <version>`. Coordinates are immutable from their first local publication, including a failed check build; choose a new coordinate before changing product bytes. Older SNAPSHOT compilation safeguards use a task-owned cache keyed by the actual library SHA-256 on remapped targets. That defensive cache does not authorize overwriting a frozen input, and SNAPSHOT publication is not retained native qualification.

The current controls exercise actual server registration, source identity, bounded workers, native registry/tag capture and identifier lookup, file initialization/preparation/persistence/publication, unchanged reopen and native shutdown cleanup. The report records the actual Java runtime and loaded library location. Compilation and a normal process exit do not establish a passing native outcome.

Dedicated runs also exercise the loader-registered command tree through the actual server console and Brigadier dispatcher. Native permission reduction and a foreign feedback source must refuse. Unknown operation lookup consumes no editor lease; file commands stage without writing, then save and restore disk/runtime values explicitly. NeoForge queries its actual registered TOML owner too. A separate native search provider checks retained pages, watch notices, cancellation, actual ticket ownership, late settlement and shared capacity. It prepares one flat FULL chunk before its no-create `STRUCTURE_STARTS` request. The 1.21.1 fixture widens only ticket-table/key observation; 26.3 uses public `TicketStorage` with distinct nonpersistent type identities. These declarations belong to the addon fixture, never the library. Native console output is bounded and temporary logger appenders close. Player and held-effect flows retain separate qualification.

`python3 tools/native_bare_probe.py --target <target> --library-version <frozen-version> --java-home <jdk25>` instead boots the library without addon sources, resources or a consumer container. Its separate build/run directories keep that classpath distinct. After real native readiness, it checks the loaded entry class, versions, actual loopback listener and absence of library settings/workers, then sends `stop` through the console and repeats after reopen. The common dedicated factory seeds loopback/port 0 before launch; changed/missing network settings refuse. This is a POSIX host qualification tool using `lsof` and `jcmd`, not a product dependency or client-menu check.

The shared registered-owner backend fixture can also run on NeoForge 26.3: `python3 tools/native_addon_server_probe.py --registered --target neoforge-26_3 --library-version <frozen-version> --java-home <jdk25>`. It uses actual LOCAL, preserves the owner/draft assertions from the 1.21.1 COMMON fixture and retains a small native registry supplement. Complete reference scenes and actual server-synced bindings remain separate. Only fixture source is shared; neither helper is distributed in the library.

`--client` selects the separate GUI fixture and requires current coordinated desktop access. It waits for the native loading overlay to clear, opens an actual form, focuses a native text field, dispatches a Unicode event, commits through the shared GUI service and checks saved reopen. Native framebuffer images and a bounded interior glyph-pixel check detect transparent value text that a successful save would miss. Independent editors close explicitly before the next opens. At exit, a fresh READY editor must close with its document runtime; a normal process exit or runtime closure alone is insufficient. To stop a running owned client fixture cooperatively, create `platform-cancel` in that fixture's run directory; the next native tick stops its actions and exits with a failed result.

NeoForge client runs also bind a real registered CLIENT TOML, refuse a native-invalid backend preflight, save through the native serializer, retain its comment and unedited field, and verify the actual reload callback thread and unchanged reopen. They do not certify delegated/server native owners, complete restart/source semantics, integrated-server host presentation, reconnect/respawn, deep key-owner failures, OS pickers or creation flows. The larger [NeoForge 1.21.1 example](../native/README.md) retains its applicable capability controls. [Verification](../../docs/development/verification.md) owns actual run results; this fixture description is not a claim that every configured target passed.

Dedicated NeoForge runs also exercise the real server-bound native config (`SERVER` on 1.21.1, `SYNCED` on 26.3). On NeoForge 26.3, `--synced-world-override` selects a separate scenario with distinct installation defaults and an existing world override. The test requires the actual native path, saves/reopens the world source and checks that installation defaults remain byte-equal. It does not change loader configuration semantics.

Client runs additionally register real native Controls entries and exercise the public key factory: native pointer/keyboard/mouse capture, loader-specific Shift behavior, draft-only application, actual Options persistence, unselected mapping preservation and saved reopen. Backend preflight is distinct from draft type validation. Operation completions explicitly return to their native executor, and actor readiness alone does not imply the screen has rebuilt its widgets.

`--client --init-failure` injects a controlled owner-construction exception and a separate structured policy refusal through the public client-file factory at actual native setup. Both must remain unavailable without effective defaults or source IO. The runner also requires the original unexpected cause in the native log and refuses an unexpected-error log entry for the policy refusal. This is not general fault-injection or cleanup-failure qualification.

`--client --world-client` adds an isolated native flat world and a second connection to it in each JVM. It checks an actual server-issued command component through the native click-action handler, real ChatScreen Enter submission, a public integrated policy form, persistence, native permission revocation/restoration, player-list respawn, disconnect cleanup and a fresh connection/context. The recipient follows a replaced player on the same play connection while an editor bound to the old player is refused. The 26.3 helper exposes the native protected click handler for the received style; it does not synthesize an attended client source. Temporary worlds are removed with the fixture. The held owner checks below qualify specific in-flight boundaries; creation recipes, client-only invocations, gameplay death and TCP retain separate scope.

The integrated flow also types a real server search command and clicks its issued Next link after a ranking change. Received native Components must preserve the captured page. Watch/coalescing, actual permission changes, cancellation and stale navigation against a successor use the current player and connection. State retires with actual server stop. This remains separate from held in-flight effect/disclosure qualification and a real discovery provider's scheduling.

A separate held policy binds the shared native command bridge to the actual player's editor and a caller-owned JSON store. Worker barriers separate pure preparation from an admitted write. Native permission loss or same-connection player replacement must prevent the former's persistence; the latter retains a saved/refused-application receipt with no private observation. The actual late reply guard must suppress completion disclosure. A fresh authorized editor permits explicit apply/recovery and exact source restoration. Direct respawn includes the native packet handler's assignment of the replacement to its connection; a player-list call alone leaves incoming commands on the old player.

The world flow also stops actual integrated servers during held preparation and after storage returns a physical write. Native context closure precedes worker release. Preparation must preserve the original file; a completed write must retain its saved/unavailable/redacted receipt. The worker and operation drain without a late reply. The next JVM observes the persisted value before explicit reset. These controls remain separate from held client-only invocation authority across respawn, remote TCP, process-crash recovery or arbitrary foreign-listener draining.

`--client --recipe-client` instead opens the actual unsaved world-creation UI, selects the native flat preset and edits a small typed projection. Its owner retains a separate immutable input larger than 2 MiB. Shared GUI operations admit a native generator change, preserve unedited dimensions and round-trip it with the loaded native `RegistryOps`. Stale construction and a basis changed before Apply must retain traceable refusals. The expanded scene also retains the existing explicit preview/cancellation/drain controls, reviewed complete save/export, stale-effect refusal, deliberate post-native-update callback failure and unknown-outcome recovery. Defaults use separate missing/eager/malformed sources, explicit save/import/undo/admission and a real second-JVM saved reopen. The malformed source is deliberately reseeded before each boot; saved valid defaults and first-boot reviewed output remain available for reopen checks. Captures are allowlisted and retained before fixture cleanup. Native actor completion does not itself establish that a screen has processed its queued synchronization, so input waits for the usable control. Shutdown verifies the managed recipe/defaults lifetimes. No server is started. The projected owner input is a fixture contract, not a complete Skyweave generator or a general data-pack migration test.

`--client --commands-client` selects an isolated integrated-world command fixture instead of replaying the rich authoring screens. It uses actual ChatScreen submission and the registered native source, with pure suggestions parsed from the same branch and source. The scene targets basic read/edit/validation/review/export/save/status/cancel operations, registered-source import and source-conflict commands, replay refusal and explicit restoration of the fixture file. Its own result and actual owner shutdown are required for success. A separate held-read scene keeps an explicitly caller-owned installation context alive across actual world stop/reconnect. The read finishes, but the departed invocation cannot accept or disclose its preview; a new explicit preview acquires current authority. No draft staging or file write follows from preview. Verification records the qualified products and assertions; held writes, server stop during persistence, player replacement and native suggestion-widget navigation remain separate. Suggestions use the same public branch and captured native source in a separate dispatcher. Reply capture uses the ordinary typed consumer, not a rendered-chat observation.

`--client --workflow-client` selects the retained-workflow regression alone. It uses JSON, actual native Controls and registered or portable client/default sources, then checks nested aliases, cached filters, independent drafts, source-specific saves, competing revisions and late close/discard decisions. A second JVM verifies completed saves and discarded client drafts. The scenario is separate from `--workspace-client` because both deliberately write the same example source; combining them would make their saved-value expectations depend on scene order. It requires its own PASS and managed-workflow shutdown evidence.

`--client --isolated-scene operations` selects the existing operation-presentation checks separately. It exercises named actions, retained result inspection, responsive details, pending cancellation, close refusal, and notice lifetime without replaying the unrelated workspace scenes. Each boot must retain the same handle while work drains, clear the settled close notice, and preserve unrelated feedback. This READ-only fixture does not produce a saved or applied receipt. The option cannot be combined with another scenario.

`--client --authoring-client` selects portable recursive, numeric, reference, collection, dependency, import, conflict, catalog, inspection and composed-workflow controls adapted from the existing native baseline. Actual text/pointer input covers lists, maps, sets, optional/default values, tagged alternatives, canonical units, paired ranges, slider dragging and explicit save/reopen. The numeric source begins malformed and must retain that data until explicit repair/retry. Its actual native window resize and GUI scale 3 check a narrow layout without replacing controls or losing caret/selection. File imports exercise preview, retained invalid drafts, held-read cancellation and explicit save; source conflicts exercise separate resolution, failed-read repair and conditional-save refusal. The focused catalog also exercises real language/font reload and wide/narrow reflow with retained input. A composed workflow retains JSON, actual Controls and registered/local source owners, hierarchical aliases, busy/dirty states and per-document receipts through separate saves and late close decisions. NeoForge uses actual CLIENT plus COMMON/LOCAL registrations; Fabric uses explicit file owners. A managed workflow remains alive until native shutdown. The driver waits for native overlays to clear before input or capture. Frame captures are copied from a bounded allowlist before cleanup. Native narration collection observes structure and contextual labels; it does not exercise spoken output. Inspection retains invalid drafts, related-field navigation and exact value export; its separate native ChatScreen review command uses an independent actor after the GUI closes. This mode does not imply other command variants, all layouts, input-method/spoken-output or OS-picker coverage.

`--client --chooser-client` selects actual OS-dialog controls independently from authoring. Its external driver must operate the disposable fixture's native dialogs; a drop event or stubbed chooser does not qualify it. On macOS, run `python3 tools/native_chooser_driver.py --target <target> --boots 2` alongside the selected probe, while holding coordinated desktop access. The opt-in driver uses system Swift/Accessibility for SDL's actual PID-owned sheet and the older picker subprocess, with explicit PID checks. It verifies the live fixture JVM and working directory, bounds actions to five identified requests per session, and uses a new session ID for reopen. Its SDK/compiler is host test tooling, not a library dependency. Chooser launches track only their actually observed helper descendants and recheck native birth identities before retiring them after terminal/failed runs; wrapper process-group termination alone is insufficient for an escaped helper. The scene separately checks Cancel, Unicode selection, explicit preview, entered-screen abandonment, duplicate-dialog refusal, late-result suppression and reuse after drain. `--manual-input` on the external driver instead observes entry/completion while a person selects or cancels; its receipts identify manual assistance and do not claim automated keyboard input. Both paths retain the same native import assertions. OS interaction has a five-minute scene budget, distinct from deterministic widget sequences. This driver qualifies the selected macOS English-dialog environment; it does not establish another OS, language, accessibility tool or window provider.
