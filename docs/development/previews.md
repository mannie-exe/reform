# Preview preparation

The 0.4 development API supplies read-only input capture, bounded graphics data, a shared workflow host, and private native mesh adapters. Exact native and consumer qualification belongs in [verification](verification.md); implementation alone does not qualify every provider or the complete system. The [presentation contract](../design/presentation-0.4-api.md) owns the complete selected behavior.

## Capture the actual draft

Call `ClientEditor.capturePreview(entryPoint, expectedDraftRevision)` on the client thread. It uses the same retained form and `DocumentActions` as editing and saving. Unaccepted native input, pending native edits, unavailable sources, and an old revision refuse capture. The underlying actor performs complete validation and checks actual READ authority before and after preparation. Capture neither saves nor applies values, and it does not require WRITE authority or approval of a save review.

`ClientPreviewCapture.sourceOperation()` exposes the actual backend inspection receipt. Its `completion()` yields `DraftPreviewInput` only after client-thread input and cached reference identity checks. A completed backend inspection does not guarantee successful native delivery. Keep these observations distinct. Closing the editor abandons delivery; cancellation requests do not prove that entered backend work stopped.

`DraftPreviewInput` contains the complete snapshot-policy-frozen candidate, provenance, observed reference stamps, and a `PreviewInputStamp`. The latter identifies both the accepted draft revision and native input epoch. Reflow or caret movement alone does not edit that epoch. A captured reference stamp is an observation, not permission to read its source. Domain providers must capture and recheck their actual resource generation separately; a resource name or human revision string cannot establish freshness.

## Frozen graphics data

`GraphicLimits` supplies explicit positive input-byte, output-byte, decoded-pixel, resource-count, and native-allocation allowances. There is no unlimited fallback or guessed standard budget. Aggregate accounting and actual native preparation must enforce the admitted operation's allowances, not merely each individual texture's bound.

`GraphicMesh` freezes positions, normals, UVs, triangle winding, material identities, and lighting declarations. UVs address each material's animation frame rather than a borrowed atlas or the full encoded strip. `geometryBytes()` describes the canonical geometry and identity payload; it does not estimate JVM or GPU allocation. An empty face list is ready invisible geometry. It has no materials and zero bounds. A viewport must retain a finite default camera for that zero extent, without inserting geometry or dividing by the extent.

`GraphicMaterial` and `GraphicLighting` preserve alpha, culling, sampling, direction, emission, and shading choices. Their presence is not evidence that a native adapter supports every combination. Preparation must implement an admitted combination or report its unsupported capability explicitly. Do not invent unresolved world tint or silently substitute one material policy.

`GraphicTexture` freezes PNG and optional metadata bytes. Construction checks the leading header and whole-strip pixel allowance before native allocation. `validatePng()` separately checks container completeness, chunk checksums, one leading IHDR, image data, and a final IEND. This integrity check is not a replacement pixel decoder.

`ClientGraphicImages.decodeStill(texture, limits, metadataLimits)` performs explicit CPU preparation through the game's PNG decoder and animation metadata parser. It validates the container before native allocation, checks native strip and output allowances, and closes the native image before returning copied `GraphicPixels`. No live resource manager, texture manager, or GPU upload participates. The selected still is the first declared animation frame; absent animation metadata preserves the full rectangular image. Frame dimensions, frame indices, ARGB channels, and alpha remain explicit. Animation playback is separate from still preparation.

Keep decoding and compilation outside ordinary rendering and search. The preparation coordinator must dispatch this work appropriately and check cancellation, authority, and source freshness before mounting its result. Successful decoding alone does not admit a stale result.

`ClientEditor.isPreviewCurrent(input)` checks an earlier capture against the same actual editor, native input epoch, cached reference observations, and current READ permission. It performs no IO or new capture. Invalid new text invalidates the earlier capture even before an accepted actor revision changes. Repairing a field does not restore the earlier epoch.

`ClientGraphicImages.decodeStills(textures, ledger, metadataLimits, reservedOutputBytes, checkpoint)` prepares a complete batch on the caller's worker. It checks aggregate encoded input and full-strip pixels before decoding, subtracts reserved geometry from the combined frame-output allowance, and charges temporary native images and exact encoded native buffers to the same `GraphicLedger` as graphics awaiting retirement. Each entered decoder needs two resource units and native bytes for its full RGBA strip plus its encoded PNG; metadata is a separate input-byte allowance. Both reservations precede allocation. A failed admission leaves no outstanding reservation. Duplicate texture identities refuse. Its checkpoint runs during admission and around each decode; cancellation or failure returns no partial map. The caller owns cancellation and job scheduling. The returned immutable map contains detached pixels, with each temporary native image closed. A reservation is refunded only after its actual native release succeeds. Image and buffer cleanup are attempted independently; uncertain cleanup retains that allocation and the original cause, even if other cleanup succeeds. The host records `preview.release_failed` once without reopening a closed view or replacing a newer result. This ledger measures known payload, not the native decoder’s internal scratch space or allocator overhead. This method neither captures resources nor publishes textures.

## Private mesh adapter

`GraphicScene` binds a frozen mesh to explicit materials and already-decoded `GraphicPixels`. `ClientMeshGraphic.prepare` performs native preparation on the client thread; ordinary drawing receives only a camera and measured viewport. The default adapter supports explicit alpha, culling, sampling, emission, and studio directional lighting. Ambient occlusion requiring world context refuses rather than becoming a silent approximation. Empty geometry needs no native allocation.

Minecraft 1.21.1 uses a private OpenGL program, buffers, textures, and framebuffer while restoring the borrowed native GUI state. Minecraft 26.3 uses its native rendering device, private pipelines, and deferred GUI extraction. Neither adapter registers textures or replaces a live resource manager. Changing the camera or viewport can wait for earlier native uses before rebuilding its private target; waiting is distinct from a missing or invalid subject.

Use a ledger shared across the workflow's entered preparations and retiring graphics. Its counters describe known native image/buffer payload and owned object counts, not total process or graphics-driver memory. Closing the view revokes new submissions immediately. Actual completion controls release, and failures remain observable through the lifetime state. A supplied freshness guard must reflect the actual source, native input, and resource generation; it is checked before preparation and submission. A predicate that always returns true does not establish owner freshness.

## Typed native contributions

`GraphicScenePreparation.Contribution` is the core metadata boundary for platform preparation data. Existing `Ready(GraphicSceneData)` remains the mesh contribution. The Minecraft host also accepts `NativeGraphicContribution<I>`: a snapshot-policy-frozen input, cached typed `NativeGraphicAdapter<I>`, actual source stamp, default camera, and the same bounded facts. Encoded input and UTF-8 facts count against retained output admission. Unknown contribution kinds are Unavailable; they cannot become a lease merely by implementing the metadata interface.

The host calls `NativeGraphicAdapter.prepare` on the client thread after admission, through the existing native runtime. `NativeGraphicPreparationContext` exposes the actual client, source stamp, and shared ledger. Register an owned attachment with `context.own(resource)` **before** allocating its handles, and reserve its known payload before allocation. Returned `Prepared` content is retained automatically using a binding reservation made before preparation; it does not need a second object reservation after allocation. Borrowed game assets remain game-owned. Partial failure attempts every registered attachment. A failed release keeps its charge and actual cause.

`Prepared.draw` receives the game-specific native GUI context, measured viewport, and camera. Preparation and submission use the same exact native-use tickets as mesh graphics. Camera changes wait for earlier uses before mutating retained native state. Release runs after actual uses retire; `NativeGraphicReleaseContext.rendererDestroyed()` is an observed teardown fact, not a timeout. Adapters must balance their native scopes, never replace global resource managers, and explicitly report unavailable context or unsupported capabilities. The wrapper preserves the native GUI state it owns; it is not a sandbox for arbitrary foreign renderer side effects.

`ClientLoadedGraphics.items(limits)` uses `ClientItemSubject.copyOf(stack, limits)` to capture a defensive stack copy through the actual native optional item codec and available registries. The immutable wire subject retains JSON and its observed native registry epoch, not an inventory, level, or live stack. Native registry decoding and model preparation happen explicitly on the client; wire serialization is effect-free. Reusing a copied subject after its connection/level context changes refuses as stale; recapture from the actual new context. Pack reloads invalidate the prepared model without inventing another registry epoch. Context observations use weak references so an inactive provider does not retain a disconnected level.

Minecraft 26.3 supplies item defaults through the actual joined world's registry components. A nonempty item at the title screen is therefore Unavailable; neither the provider nor the fixture binds synthetic components into global holders. Empty items remain valid. Minecraft 1.21.1 can use its actual built-in registry defaults without a joined world. Missing required context is distinct from malformed copied input. The ordinary slot never reads an inventory or ticks a world; an integration test may join its separately owned disposable world to qualify native behavior.

Both item implementations cache the native GUI model/state and render it into the same owned framebuffer/compositor used by mesh views, attached to the enclosing native lifetime. They preserve their actual native materials while avoiding magnification of a small GUI icon cache. The 26.3 implementation calls the public feature renderer at actual GUI consumption, with the native GUI lighting context. Its pending action belongs to the already-entered exact GUI-state ticket: reset discards it, revoked READ/source/visibility prevents domain work, and GPU completion still controls target release. Deferred faults remain logged and observable without throwing into the baseline GUI loop.

Camera rotation changes three-dimensional native transforms before the authored item transform. Camera and viewport changes wait for earlier native uses; unchanged frames do not compile another model. Prepared geometry is static; borrowed atlas, foil, and shader effects follow the native renderer. Game-owned shaders, shared feature buffers, and assets are not host-owned allocations and must not be reported as released host memory. The owned target, projection buffer, views, and sampler use the aggregate ledger, and the target extent has an explicit image allowance. Zoom changes the pose inside that fixed target rather than allocating a larger game-owned image cache. The prepared 26.3 layer count is bounded. These implementations and their scoped native-state restoration still require the actual-client checks recorded in verification; compilation alone is not native qualification.

### Static block states

`ClientBlockSubject.copyOf(state, limits)` captures the actual native block-state codec without a position, level, inventory, or block-entity payload. Wire decoding is effect-free and accepts only native name/property strings. Client-stage native decoding must round-trip the complete state; an unknown or invalid property cannot silently become the native codec's fallback state.

`ClientLoadedGraphics.blocks(limits)` prepares the loaded static state model through the same typed native contribution, host, ledger, and retirement coordinator. It never renders an item as a block substitute. Invisible and zero-quad models are ready empty geometry. Non-static render shapes report their separate capability; this provider supplies only the static base model, including for states that also have a block entity. An empty static base does not imply that the complete block-entity appearance is empty. Missing models, malformed states, unavailable resources, and budget refusals remain distinct.

Native layer/part selection and tint capture occur during explicit client preparation. Minecraft 1.21.1 captures actual native quads and isolated display layers, then submits those quads through the native bulk vertex API. Minecraft 26.3 retains actual prepared block-model parts and uses the native feature renderer; NeoForge retains its per-quad material submission path. Both use measured owned targets with the same native state scopes as item views. Bounds come from actual native vertex positions; camera fitting preserves their proportions. Non-finite or unrepresentable native transforms refuse instead of producing invalid matrices.

The provider uses native isolated-model lighting and context-independent default tints, without claiming world ambient occlusion, biome tint, neighbor culling, a running block-entity renderer, or world shader parity. It does not create a world, insert or tick an object, or mutate loaded assets. Part/layer and tint counts use the resource allowance. Canonical quad geometry is bounded at 128 bytes per quad against the output allowance; that bound is not a JVM allocation estimate. Borrowed game models, atlases, and shared native feature buffers remain game-owned. Private targets and their known payload stay on the aggregate native ledger. Native qualification belongs in [verification](verification.md), independently of compilation.

## Hosted preparation

Obtain the host with `workflow.graphics(limits, maximumViews)`. The workflow fixes this explicit aggregate budget and view bound once, across both source kinds. Opening a view alone does not prepare it.

### Loaded resources

`host.openLoaded(provider)` opens a read-only loaded-resource view without admitting a settings document. `ClientLoadedGraphicProvider<S>` receives a `LoadedGraphicRequest<S>` under the workflow's actual READ operation and context. It receives no edited settings, fabricated draft revision, or write capability. `ClientGraphicProvider<T, S>` retains its separate complete-draft capture and native-input guards. Both kinds use the same bounded lane, worker/native stages, ledgers, visibility, cancellation, and actual-use retirement.

`GraphicSourceStamp` distinguishes `DRAFT` from `LOADED`. The existing `GraphicRequest.Stamp` retains its exact `PreviewInputStamp`; `LoadedGraphicRequest.Stamp` carries the actual loaded resource identity instead. `GraphicSceneData`, `PreparedGraphic`, and host results expose that common source stamp. A caller inspecting draft-only data must first match the actual draft subtype. A loaded image is never evidence that edited settings compiled or applied.

`ClientLoadedGraphics.textures(limits, metadataLimits)` prepares one exact local PNG resource from the loaded client packs. It reads bounded image bytes and metadata from the same contributing pack, closes its streams, and uses the shared still decoder and native allocation ledger. The first declared frame is fitted at its own aspect ratio, with nearest filtering, alpha, and unlit reference presentation. Missing assets are Unavailable; malformed data and budget exhaustion remain explicit failures or refusals. It neither browses a filesystem nor accepts remote URLs.

The client-only reload adapter observes the actual Minecraft resource manager, before replacement and after its real completion. Start, completion, and closure change the snapshot identity even when the human revision text is unchanged. Late completion cannot make a newer reload ready. Separate server-data or mod-owned managers do not change this source. Reload retires old images; returning to a view does not prepare another image automatically. A failed or unfinished reload keeps resources unavailable.

`ClientLoadedGraphics.sprites(limits)` captures a loaded GUI or block-atlas sprite through a `ClientSpriteSubject`. Its explicit `sourceFrame` is a zero-based physical frame in the retained source strip, not the atlas animation's current or first declared frame. A source-frame choice never advances or changes the game's animation. The client stage borrows the actual atlas image only long enough to copy its complete bounded RGBA strip to owned heap pixels; it neither closes nor mutates that image. Worker preparation crops the selected frame and preserves its colors and aspect through the same private mesh adapter. No game-owned sprite or image enters the prepared result. Missing atlas entries are Unavailable rather than an implicit missing-texture preview. Invalid frame choices and capture/output allowances refuse explicitly. The input-byte allowance covers the complete copied strip; the frame has the usual separate output/pixel admission. Capturing native atlas pixels is an explicit client-stage cost; rendering and search never repeat it.

`ClientViewContent.LoadedGraphic<S>` adds a shared loaded-image slot to an authored custom body. Supply a readable title/help, the typed provider and frozen subject, and the workflow's explicit aggregate limits/view bound. It admits no editor and performs no preparation during projection. **Prepare loaded image** is explicit; camera controls change only the view. **Show loaded image** focuses and reveals the current native viewport after dispatch. Unchanged slots survive ordinary custom-state refresh/reflow; replaced, removed, hidden, and closed slots retire their actual interests. Cancel is enabled only for queued or entered preparation; camera changes require a ready image. Image details retain preparation status, current versus earlier image provenance, resource/context/request identity, actual failure cause, and source facts. Inspecting those cached observations does not prepare, retry, read files, or save. Custom bodies without an active document do not show a misleading prompt to edit settings. A draft catalogue task continues to use `ClientTaskGraphic`, with its actual document input.

For example, create a provider once in an admitted custom-view factory, then return a cached declaration from its projection:

```java
var textures = ClientLoadedGraphics.textures(limits, metadataLimits);
return () -> new ClientViewContent(List.of(
    new ClientViewContent.LoadedGraphic<>(
        "logo", Component.literal("Pack artwork"), Component.empty(),
        textures, "example:textures/gui/logo.png", limits, 1)));
```

The declaration is a loaded-resource view. To preview edited profile output, use the actual document provider instead.

### Draft providers

Open a draft view with `host.open(workflow.editor(definition), provider)`, using the exact retained owner definition. This does not load another editor, prepare a subject, or grant READ permission.

`ClientGraphicProvider<T, S>` supplies a stable provider ID, a `ValueType<S>` for bounded selection parameters, explicit limits, a cheap actual `ReferenceStamp` for its resources, and a preparation function. Its request contains the complete separately captured `DraftPreviewInput<T>`; do not serialize the full document or texture payload into `S`. Selection parameters use the existing operation input admission. The provider composes `ClientGraphicWork.onWorker` and `onClient` stages rather than waiting for a worker result on the client thread. Native stages prepare detached model data; private GPU allocation stays with the host. Each stage must close its own transient resources before returning detached data.

`GraphicScenePreparation` is the provider's CPU/native-data outcome. Ready contains frozen `GraphicSceneData`: exact request stamps, mesh/texture bindings, default camera, and bounded descriptive facts. It has no GPU lease. The host checks the complete identity and provider allowance again before native preparation. Known UTF-8 fact payload counts with geometry and pixels against output admission.

`view.request(subject)` explicitly requests preparation. One expensive request enters at a time per workflow; each viewport retains only its latest pending request. A replaced pending attempt has no invented operation handle. Once entered, its `Attempt.operation()` is the actual `OperationScope` handle. Cancellation does not release the lane until entered work is terminal. Provider child ledgers narrow their limits while sharing atomic reservations with the workflow parent, including native work still retiring. Retained scene output has a separate aggregate payload counter.

The operation receipt and `Attempt.completion()` retain only bounded result metadata. They do not retain decoded scene payload or a GPU lease. `view.preparation()` separately exposes the current native `GraphicPreparation`; only Ready contains a `PreparedGraphic` lease. Its `close()` revokes new drawing, while `releaseCompletion()` reports actual release success or failure later. Cleanup does not depend on an open editor executor. Inspect the returned state rather than treating future completion alone as proof of successful release.

A native draw can still refuse after CPU and GPU preparation, for example when the measured framebuffer exceeds its native allowance. The hosted viewport retains that `PolicyRefusal` report and exposes Refused, including the specific budget cause, then retires its native lease through the same tracked cleanup path. Other draw exceptions remain Failed with their actual cause. Neither outcome implicitly retries preparation; admitted preparation metadata is not proof that a later draw succeeded.

The host observes each actual release completion even after the view closes or loses its current graphic interest. A failed release retains the uncertain output charge, exposes `preview.release_failed` in the view snapshot, and records its actual cause through `releaseFailure()` and `releaseFailureCount()`. Synchronous and deferred failure paths count the same lease once. A cleanup issue remains available separately from the current preparation outcome: an older lease cannot replace a newer request's result or reopen a closed view. Inspection does not retry native destruction or require restoring editor authority.

Draft, native-input, permission, or resource-identity changes prevent old native submission and cancel obsolete preparation. Hiding or closing a view does the same. Showing it again does not silently prepare, save, or reload anything. The prior result's bounded facts and provenance can remain available as historical information while its status is Stale. No result with another view/request/source stamp can mount.

The host is integrated with authored loaded-resource slots and registered draft tasks. Exact native and consumer checks remain attributed to their tested candidates in verification. Consumers should use these shared compositions rather than create a private production screen or coordinator around the viewport widget.

## Isolated native chest references

`ClientLoadedGraphics.chests(limits)` accepts `ClientChestSubject`: normal or trapped single chest, with finite lid progress from zero to one. This explicit reference is independent of a saved or edited domain profile. It never copies an inventory, block-entity NBT, world position, or level, and it does not insert, tick, open, or pair a chest in the world.

Preparation creates a fresh native chest renderer and fresh baked model parts using the actual loaded model set, textures, and native dependencies. It does not borrow the live dispatcher's mutable renderer or replace a model/resource manager. The 1.21.1 adapter invokes the native chest renderer directly; the 26.3 adapter extracts detached native state and uses native feature submission. The game's native lid easing, seasonal material choice, geometry, UVs, and shading remain native. This is a static full-bright single-chest reference, without world lighting, neighboring halves, gameplay animation, or arbitrary modded block-entity rendering.

A preparation-only vertex sink measures actual posed native vertices and enforces the canonical position/normal/UV allowance before GPU allocation; it retains no replacement mesh. That allowance is not a measurement of baked model object memory or allocator overhead. Three native model layers are required by the actual renderer constructor. Owned surfaces and outstanding native uses share the existing host ledger and retirement protocol; borrowed native assets are never closed by this provider. Native qualification and material limits belong in [verification](verification.md).

## Native ownership

`RenderLifetime` separates a view's interest from outstanding native uses. Closing it prevents new uses; resources release only after every acquired use retires. Release entry, successful completion, and failure are separate observations. A failed partial release is retained rather than retried as if nothing happened.

Only an adapter's actual native consumption or GPU completion can retire a use. A timer, a screen close, or a similarly named game frame callback is insufficient. The 26.3 renderer's extraction and deferred submission differ from 1.21.1 drawing. Each binding must also drain or reconcile its uses before its actual renderer or device shuts down. Core lifetime tests do not establish that native binding.
